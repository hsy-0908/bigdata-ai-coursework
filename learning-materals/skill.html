概念学习模块

Skill

智能体技能 · Agent Skill — 一种给 AI 智能体装载专业能力的开放格式

一个 Skill 就是一个装着 SKILL.md 的文件夹：用元数据告诉智能体「我是谁、什么时候该找我」，用 Markdown 正文告诉它「具体怎么做」。智能体按需加载它，而不是每次都全量塞进上下文。
由 Anthropic 于 2025 年 10 月随 Claude 产品首发，2025 年 12 月作为开放标准释出（agentskills.io），现已被 25+ 款智能体产品采纳。

02它解决什么问题

程序性知识以前住在三个糟糕的地方

每个跟智能体打交道的团队都会积累一套「我们这儿做事的方法」：发布前要跑什么清单、代码评审看哪些点、周报什么结构。在 Skill 出现之前，这些东西只有三种归宿——

坏地方 1

人的脑子里

于是每次都要在对话框里重新敲一遍。人是会忘的，新人是不知道的，同一个流程十个人有十个版本。

坏地方 2

越写越长的指令文件

全塞进一份 CLAUDE.md / 系统提示词。结果无论这次任务相不相关，智能体每次请求都得扛着全部内容，上下文被稀释，还互相干扰。

坏地方 3

工具专属的配置格式

为 A 工具写的流程，团队里用 B 工具的人得重写一遍。知识被锁死在工具里，换工具就归零。

Skill 的答案是：把流程写成带版本控制的文件夹。进 Git、能评审、能复用、跨平台。

03形态

一个文件夹，一个必需文件

pdf-processing/
├── SKILL.md        # 必需：元数据 + 指令
├── scripts/        # 可选：可执行代码
│   └── extract.py
├── references/     # 可选：按需加载的文档
│   └── forms.md
└── assets/         # 可选：模板、图片、数据
    └── template.md

只有 SKILL.md 是强制的，其余三个目录是约定俗成的命名，也可以放任何别的文件。文件一律用相对路径从技能根目录引用。

06最关键的技巧

description 是触发器，不是摘要

绝大多数「技能不生效」的故障，问题出在 description，而不是指令正文。因为发现阶段智能体只看得到这一句话——写得太短它匹配不上，写得太宽它到处乱触发。

太模糊
description: 帮助处理 PDF。
写清做什么 + 何时用
description: 从 PDF 提取文本与表格、填写表单、合并文档。当用户提到 PDF、表单或文档抽取时使用。
只覆盖一种问法
description: 当用户说「review my code
for security issues」时使用。
覆盖同义说法
description: 审查代码中的 bug、安全漏洞与风格问题。当用户要求 review 代码、检查 PR、审计改动、找 bug 或提到代码评审时使用。
在违规之后才触发
description: 当你忘记写测试时使用。
在违规之前就介入
description: 在实现任何功能时、写第一行代码之前使用。
总是误触发
description: 为源码生成单元测试。
加否定边界
description: 为源码生成单元测试。当用户要求写测试、补覆盖率时使用。不要在运行已有测试或修复失败测试时使用。

验收方法：写完后准备 5–10 条应该触发的说法、几条间接说法，再加 2–3 条不该触发的说法，逐条检查。间接说法没命中，就补触发词；否定用例命中了，就补「不要」边界。

07边界

Skill 不是什么

它常被和这三类东西混淆。区别在于各自回答的问题不同：

本文主角

Skill

「该怎么做？」

程序性知识的打包格式。教智能体按什么流程做事，可携带脚本与模板。

MCP

「能碰到什么？」

连接外部工具与数据源的通信协议。给智能体「手」。

Prompt

「这次说什么？」

单次、即用即弃的指令。不持久化，不复用。

Subagent

「谁来干？」

独立上下文的执行单元。管的是隔离与分工，不是知识。

Skill 与 MCP 是互补而非竞争：一个 Skill 可以描述「依次调用三个 MCP 工具的流程」，MCP 负责真正连上去。前者是剧本，后者是手。

08反模式

点开看看最常见的坑

把通用知识抄进技能

在 SKILL.md 里写「Python 函数用 def 定义」这类模型本来就懂的内容，只会稀释上下文，把真正的增量信息淹没掉。

判据很简单：删掉之后模型会不会做错？不会，就该删。真正该写的是模型搜不到的高语境信息——比如「调用服务 X 的 API 必须带 X-Client-Version: v2 头，否则返回 403」。

SKILL.md 越写越长

超过 500 行就该拆。把详细示例、进阶用法、变体说明移到 references/，然后在正文中明确写清「什么情况下去读哪一个」。

引用要只深一层——不要在 references 里再套 references，否则加载链路会失控。

正文里反复出现「本技能……」

智能体已经知道它在读一个技能了。反复自我指称纯属浪费 token。直接写「审查 TypeScript 代码库中未使用的导出、循环依赖和死代码路径。」就好。

目录名和 name 字段对不上

规范要求 name 必须与父目录名完全一致，且文件名必须是全大写的 SKILL.md。skill.md、Skill.md 都不会被发现。

合法：pdf-processing、data-analysis。非法：PDF-Processing（大写）、-pdf（前导连字符）、pdf--processing（连续连字符）。

不写「什么时候不该用」

这是投入产出比最高的一处修改。明确划出边界——「不适用一次性临时分析」「不处理 PDF、图片等二进制文件」「想要重构建议请改用 code-review 技能」——能大幅减少误触发。

把 description 写成工作流说明

如果 description 把流程讲完了，智能体可能觉得「我已经知道了」，从而跳过加载正文。

记住分工：description 负责匹配，正文负责执行。description 里放触发条件，不要放操作步骤。

10动手

现在写一个你自己的

练习：把你最常重复解释的那件事写成技能

  1. 找出一件你跟 AI 解释过三次以上的事——周报格式、提交信息规范、某个数据表的坑。
  2. 建目录 ~/.workbuddy/skills/<你的技能名>/，目录名全小写、带连字符。
  3. 写 SKILL.md：frontmatter 只填 name 和 description，两个都填满约束上限的一半以上。
  4. description 按「做什么 + 何时用 + 何时不用」三段写。
  5. 正文里只留模型自己猜不到的内容，并加一节「注意事项与常见陷阱」。
  6. 拿 5 条该触发、3 条不该触发的说法去测。不中就改 description，别改正文。
  7. 超过 500 行就拆 references/。

判断一个技能写得好不好的最终标准只有一条：下次遇到同样的事，你还需要再解释一遍吗？
