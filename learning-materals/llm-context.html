上下文窗口（Context Window）

模型一次推理时，能同时"看见"的全部内容的上限。它更接近工作台面，而不是硬盘。

上下文窗口是模型在单次请求—响应中能处理的 token 总量上限。你的系统提示、对话历史、粘贴的文档、当前问题，以及模型自己的回答，全部共享这同一份预算。
类比：一张固定大小的工作台。台面上摆不下，就得把东西拿走，或者只把用得上的零件拿上来。台面变大不会让人更聪明，只是少跑几趟。

台面上都摆了什么

系统提示词 5% 对话历史 20% 检索资料 40% 当前问题 5% 回答预留 30%

前四项相加 = 你付的输入成本；最后一项 = 留给思考和输出的空间。多塞文档，就是从这个预算里抢。

为什么它会满

模型没有跨轮次的"记忆"。每一轮对话，你都在把上文整包重发一遍。所以 token 消耗只增不减，长对话必然撞顶。撞顶后只有三条路：

做法代价
截断最早内容丢掉开场立下的规则和约定
把历史压成摘要省空间，但细节不可逆地丢失
只取相关片段（检索）最省，但需要预先建索引

三者本质相同：减少真正进入窗口的 token。区别只在于由谁决定丢什么，以及丢掉的还找不找得回来。

三个反直觉的事实

1. 标称值 ≠ 可用值 厂商宣传的 "1M" 是能塞进去的上限，不是能可靠用出来的上限。长输入里模型对中间位置的信息召回明显偏弱（lost-in-the-middle），开头和结尾最可靠。
2. 更大的窗口不会让模型更聪明 窗口只是容量指标，不是能力指标。塞满窗口往往比精准投喂 20K 的效果更差，而且贵得多。
3. 成本随长度非线性上升 你按每一个送进去的 token 付费；部分厂商对超过阈值（常见是 20 万 token）的请求加收长上下文费用，单价可能翻倍。RAG 管道很容易悄悄把每次请求推过这个档位。
截至 2026 年中，主流前沿模型的窗口集中在 1M token 量级（Gemini 2.5 Pro 1,048,576；GPT-5.5、Claude Opus 5、DeepSeek V4 均为 1M；GPT-5 为 400K；GPT-4o 仍为 128K）。网上流传的 10M 窗口多为未经验证的宣传口径，请以厂商 API 文档为准。具体数字变动很快，用到时再核对官网。

怎么换算成"多少字"

  • 英文：1 token ≈ 0.75 个单词 → 128K ≈ 约 9.6 万词，1M ≈ 约 75 万词
  • 中文：1 个汉字 ≈ 1 个 token（不同分词器在 0.6–1.2 之间浮动）→ 1M ≈ 约 100 万汉字

实操清单

  • 位置比数量重要。关键指令放在输入的开头或结尾，别埋在中间。
  • 先检索，再提交。大多数任务用 RAG 取相关片段，比整包塞进去更准也更便宜。
  • 历史要压缩，不要重发。把稳定的对话前缀摘要化，只保留关键结论和约束。
  • 缓存稳定前缀。系统提示、工具说明这类不变内容做前缀缓存，通常能省下大部分成本。
  • 盯住阈值。留意厂商的长上下文加价门槛，别让 RAG 把请求静默推过高价档。
  • 为输出留空间。窗口被输入占满时，回答会在半途被截断。

自测

1. 你和一个 128K 窗口的模型聊了很久，它突然开始重复你早就说过的话，还忘了开场定下的格式要求。发生了什么？

看解析

上文累积逼近上限，最早的对话内容（包括开场立下的格式约定）被截断了。模型没有跨轮记忆，它只是"看不见"了那部分内容。解法是压缩历史或重述关键约束。

2. 一份 30 万 token 的合同需要审阅。用 1M 窗口的模型整份丢进去，是最佳方案吗？

看解析

不一定是。整份塞进去会命中长上下文加价档，且关键条款若落在输入中段，召回质量会下降。更好的做法是按条款切块检索，只把相关条款 + 你的审阅清单送进窗口。

3. 把上下文窗口从 200K 换成 1M，模型的推理能力会提升吗？

看解析

不会。窗口是容量指标，不是能力指标。它决定一次能读多少，不决定读得多好。换大窗口解决的是"放不下"，不是"想不明白"。
