Concept card

Agent（智能体）

一张把概念讲透的卡片：定义边界 · 结构 · 机制 · 反直觉事实 · 失败模式 · 自测

00 定义 · 类比 · 判别式

Agent 是在循环中运行的系统：它自己决定「下一步做什么」，调用工具去真实执行，再把执行结果当作反馈重新塞回自己的判断里，直到它认为任务完成。

它不是什么（边界比定义更重要）

  • 它不是「接了工具的大模型」。那叫 augmented LLM（增强型大模型）——一次带工具调用的推理，没有循环，也没有自我判断终止的环节。
  • 它不是「全自动无人值守」。自主度是一个旋钮，不是开关。生产环境里绝大多数「Agent 系统」其实是工作流与 Agent 的混合体。
  • 它不是更聪明的模型。同一个模型套上循环，未必变强，可能只是变贵、变慢、变得更不可预测。

类比：带工具箱的项目经理

普通大模型是「你问我答的顾问」；工作流是「照 SOP 执行的办事员」；Agent 是项目经理——拿到模糊目标，自己拆步骤、自己派活、自己看结果对不对、自己决定要不要返工。项目经理的价值不在他比专家更懂，而在他承担了「下一步」这个决策。

判别式（拿去判断没见过的新系统）

写代码的时候，下一步动作就已经确定了吗？

是
工作流（workflow）。模型与工具由预定义代码路径编排，控制权在开发者手里。
否
Agent。下一步由模型在运行时根据上一步的观测结果动态决定，控制权在模型手里。

可操作检验：换一个你没预设过的任务变体扔进去。路径是你写死的，它就走不通；它能自己拐弯，那才是 Agent。

参考：Anthropic《Building effective agents》把所有变体统称为 agentic system，并在架构上把 workflow 与 agent 分开——定义以该文的表述为准。生态与框架变动快，落地时以官方文档为准。

01 结构拆解

Agent 由四部分组成，加上两个外部件。重点是：前四者共享同一份上下文预算，这是后面所有反直觉事实的物理根源。

隐藏约束：一份预算，四个用户

指令、工具定义、每一步的思考、每一次的工具返回值，全部挤在同一个上下文窗口里。加一个工具就多占一份固定开销（而且每一轮都要重新付一遍）；多走一步就多一份永久占位。所以「工具给多一点」和「让它多试几轮」这两件直觉上的好事，会在同一份预算上互相打架。

标称值 vs 可用值

模型的上下文长度是标称容量，而四个部件实际能分到的是可用容量。标称再大，长轨迹也会把预算吃满；同时要区分容量指标（能装多少）与能力指标（装得下不等于用得好）——长上下文里中间部分的有效利用率通常低于首尾，这是「lost in the middle」现象，别把装得下当成想得起。

02 运转机制

下面这条轨迹贯穿到底：「找出上周销售数据里的异常，写成简报发给张总」。

  1. 感知：把所有东西装进上下文

    把目标、可用工具清单、已有历史一起交给模型。这一刻模型还什么都没做，它只是看到了局面。

    [system] 你是数据分析助理。可用工具：read_csv / query_db / send_mail / write_file [user] 找出上周销售数据的异常，写简报发给张总 上下文 +指令 +工具定义 +目标 ← 固定开销，每一轮都要重新付一遍
  2. 决策：模型只输出「下一步」

    模型不直接给最终答案，只输出下一步做什么——要么调用某个工具，要么宣布结束。这一步是 Agent 与单次调用的分水岭。

    思考：得先知道数据长什么样、异常在哪 → 先读文件 动作：read_csv(path="sales_2026_W35.csv") 上下文 +思考 +动作
  3. 执行：动作离开模型，在真实世界发生

    工具在真实环境里跑。返回值是事实而不是模型的想象——这正是 Agent 能自我纠错的根本原因。

    read_csv 返回：12 行预览 + 列名 date, region, sku, amount, refund 其中 amount 有 3 个负值 上下文 +返回值 ← 通常是最占地方的一块
  4. 回灌与判断：由模型自己决定够没够

    返回值写回上下文，回到第 2 步。够就输出最终答案，不够就再走一轮。终止条件必须写进指令，否则它永远觉得还差点什么。

    思考：负值像是退款没拆干净 → 回原始订单表核对 动作：query_db(sql="SELECT ... WHERE amount < 0") → 未终止，回到第 2 步 上下文 +思考 +动作（前面所有内容原样保留并重付一次）
  5. 终止与交付：自己按下停止键

    模型判断条件已满足，不再调用工具，直接输出最终答案。真正的系统在这之外还会有一道硬护栏，不该只信模型的一句「完成了」。

    思考：3 个负值确认为退款未拆分，非录入错误 → 结论已充分 动作：write_file(简报.md) → send_mail(to=张总) → 终止。全程 6 次模型调用，上下文被重复付费 5 次

03 边界辨析

四者的差异不在「用了几次模型」，而在谁决定下一步、有没有副作用、会以什么方式失败——这些才是结构性差异。

形态谁决定下一步副作用典型失败方式什么时候用
单次调用
（+检索）		 无人决定，只有一步 无，纯生成 幻觉；信息不在上下文里就直接瞎编 任务能被一句话描述清楚，且所需信息可一次性塞进上下文
工作流
workflow		 开发者，路径写死在代码里 取决于节点，可在节点间设卡 遇到流程外的输入就卡死或走错分支 任务可清晰分解、路径可预设，要的是可预测与一致性
单 Agent 模型，运行时动态决定 有，且发生在真实环境 不终止 / 过早终止 / 上下文撑爆 / 错误累积 开放式问题，步骤无法事先枚举，值得用延迟和成本换性能
多 Agent 模型之间分摊角色，另有一个编排层 有，且叠加、更难回滚 子 Agent 目标漂移；互相等待；上下文重复膨胀；成本失控 子任务可真正并行且接口清晰；先把单 Agent 做到位再说

经验法则：先求最简单的方案，只在必要时增加复杂度。很多需求，一次调用 + 检索 + 示例就够了。

04 常见变体

Tool-calling loop
工具调用循环
适合：最通用的底座，绝大多数 Agent 都是它。
缺点：没有显式规划，容易在局部最优里打转。
ReAct
推理与行动交替
适合：需要「边想边查」的任务，思考过程可见、便于调试。
缺点：思考文本也占上下文；推理链长了容易自我说服。
Plan-and-Execute
先规划后执行
适合：步骤多、顺序有依赖、需要人先审一遍计划的任务。
缺点：计划一旦过时就得重排；对初始信息不足的场景很脆。
Reflection
反思 / 自我批评
适合：有明确外部校验信号时（跑测试、过编译器、对标准答案）。
缺点：没有外部信号时只会自我强化，见第 05 节。
Orchestrator–Workers
编排者与工人
适合：子任务能并行、且每个子任务边界清晰（如批量处理文档）。
缺点：编排层本身成了新瓶颈；子 Agent 之间上下文不通。
Human-in-the-loop
人在环上
适合：有不可逆副作用的动作（付款、发外部邮件、删数据）。
缺点：人成了吞吐量上限；审批点设计不好就变成橡皮图章。

05 反直觉事实

1 · 工具给得越多，Agent 越笨

结论：工具数量与任务是负相关的——每多一个工具，选择正确工具这一步就多一次出错机会，而且工具定义会挤占每一轮的固定预算。

机制：选择工具本身是一次分类决策，候选集越大，混淆概率越高（名字相近、功能重叠的工具尤其致命）；同时工具定义是每一轮都要重付的固定开销，30 个工具的详细 schema 可能吃掉预算的一大块，留给「思考与观测」的空间反而变小。所以正确答案不是「多给工具」，而是按任务动态裁剪工具集，并保持每个工具的职责互斥、命名有区分度。

2 · 没有外部信号的「自我反思」，是自我强化

结论：让 Agent 反复 review 自己的输出，常常不会纠错，只会让它更确信自己没错。

机制：反思的输入仍然只有模型自己的上下文与自己的先验——同一个分布里采样，得到的是相关样本而非独立证据。它缺少外部锚点：真实的执行结果、测试是否通过、编译器报错、检索到的原文、另一个独立模型的判断。有外部信号时反思很有效（跑测试 → 看报错 → 改代码）；没有外部信号时，它只是把同一个偏见说了两遍，而且第二次说得更自信。判断标准：你的反思回路里，有没有一步是模型之外的世界说了话？

3 · 成本主要来自「重复读同一份上下文」，不是来自「多想了几步」

结论：Agent 的账单大头是每轮把整段历史重新送进去，而不是工具调用本身或思考的字数。

机制：循环每转一圈，指令 + 工具定义 + 全部历史轨迹都要重付一次。于是总消耗大致随步数呈平方级增长：第 n 轮要读 n−1 轮的积累。这解释了三件事——为什么长轨迹会突然变贵、为什么「让它多试几轮」的边际成本远高于直觉、为什么轨迹压缩与摘要（把已完成的步骤压成结论）以及把大返回值落到文件只回传路径是最有效的两个优化。缓存命中的前提是前缀不变，所以要把稳定内容放前面、易变内容放后面。

整体成功率 = 单步可靠性步骤数。20 步时：99% → 81.8%，98% → 66.8%，95% → 35.8%，90% → 12.2%。真实情况比这条曲线更糟：它假设各步独立且单步可靠性恒定，而实际错误是相关的——一步走偏，后面每一步都在错误前提上继续决策。

06 失败模式

症状根因对症
死循环 / 步数爆炸没有写死终止条件，或工具每次返回完全相同的错误，模型重复同一动作硬步数上限 + 重复动作检测（同参数连调 N 次即中断）
上下文撑爆工具返回了整张表 / 整个网页，原样回灌返回值截断与摘要；大结果落盘只回传路径；定期压缩历史
工具幻觉调用了不存在的工具，或参数编造（文件路径、ID、日期）参数先做 schema 校验；失败时把报错原文回灌，让模型自己改
过早终止 · 假装完成模型认为「够了」但其实没验证，尤其在缺数据时在指令里写明「完成前必须满足的证据清单」；关键结论要求给出来源
不可逆副作用发邮件、付钱、删文件这类动作被直接执行副作用动作一律走人工审批或双阶段确认；默认沙箱与最小权限
目标漂移中途被某个异常发现带跑，忘了原始目标每轮把原始目标重新注入上下文末尾；长任务定期复述目标
错误累积与自我说服早期一步走错，后续每一步都在错误前提上继续，且越写越自信关键节点设外部校验（跑测试、对账）；允许整段回滚重来
多 Agent 互相甩锅子 Agent 上下文不通，各自持有矛盾假设收敛到单 Agent 先跑通；确需拆分时，明确共享状态与接口契约
成本失控步数平方级的上下文重读（见 05 节第 3 条）步数与预算双上限；稳定内容前置以命中缓存；轨迹摘要

07 实践清单

  • 先问：能不能不用 Agent。一次调用 + 检索 + 示例通常就够；需要固定流程时优先工作流。
  • 把终止条件写进指令，包括「什么证据算完成」和「什么情况下直接放弃并交还人类」。
  • 设双重上限：步数上限 + 预算上限，两者都要硬。
  • 工具集按任务动态裁剪，控制在几到十几个，职责互斥、命名有区分度。
  • 工具返回的信息要瘦身：截断、摘要、落盘传路径，别原样回灌大对象。
  • 把报错原文回灌给模型，而不是自己 catch 掉再让它重试——它需要根据具体失败原因改动作。
  • 为反思回路准备外部锚点：测试、编译器、检索原文、对账结果、第二个模型。
  • 副作用动作加审批：付款、对外发送、删除，一律人工确认或双阶段。
  • 上下文布局：稳定内容前置（指令、工具定义），易变内容后置（最新观测），以命中前缀缓存。
  • 先跑通单 Agent 再拆多 Agent，多 Agent 是复杂度的乘法不是加法。
  • 全量记录轨迹（每步的思考、动作、观测、耗时、花费），否则无法调试。
  • 用固定任务集做回归：Agent 的行为是分布，不是函数，单次成功什么都不能证明。

08 误区（点开看错在哪）

Agent 就是接了大模型的工具

缺了循环和自我终止。一次带工具调用的推理叫 augmented LLM，它不根据返回值重新决定下一步，也不会自己判断任务是否完成。判别式很简单：下一步由谁决定——写代码时就定死了，就不是 Agent。

工具给得越多，Agent 能力越强

两个方向同时变差：选择正确工具的错误率随候选集增大而上升；工具定义是每轮重付的固定开销，挤占思考与观测的预算。正确做法是按任务动态裁剪，宁可少而互斥。

让 Agent 多试几轮，成功率自然会变高

重试只有在每次尝试相互独立且带外部反馈时才提升成功率。同一条错误轨迹上的重试，每一步都在错误前提上继续，成功率按幂次衰减（见 05 节曲线）。提升单步可靠性（更好的工具报错、更清晰的指令、更小的决策空间）比增加步数有效得多。

Agent 会自己反思，所以能自我纠错

反思的输入仍来自模型自身的上下文与先验，是相关样本而非独立证据。没有外部锚点时，它倾向于给已有结论找更多理由，表现为更自信而不是更正确。真正的纠错来自外部信号：测试、编译器、检索原文、对账结果。

多 Agent 一定比单 Agent 强

多 Agent 增加的是复杂度，不是能力。它引入编排瓶颈、上下文不通、状态不一致、成本叠加等新问题，且失败更难归因。只有当子任务真正可并行、接口清晰、且单 Agent 已在同类任务上稳定跑通时，拆分才划算。

上了 Agent，就不用写工作流了

现实里几乎所有可用的 Agent 系统都是混合体：确定性的部分用工作流锁定（解析、校验、格式化、审批），不确定的部分交给模型决策。把能写死的部分也交给模型，只是在用成本换不确定性。

09 自测（8 题，每题带解析）

1. 一个系统按固定顺序调用 3 次大模型，中间用代码做格式校验与重试。它是 Agent 吗？

不是这是工作流（提示链 + 程序化 gate）。下一步动作在写代码时就已经确定，控制权在开发者。即使有重试，重试条件也是代码写死的，不是模型根据观测动态决定的。

2. 判断 Agent 与工作流的可操作判别式是什么？

答案下一步由谁决定。写代码时已确定 → 工作流；运行时由模型根据上一步观测动态决定 → Agent。检验方法：换一个没预设过的任务变体，能自己拐弯的才是 Agent。

3. 上下文里通常最占地方的是哪一块？

答案工具的返回值（观测）。指令和工具定义是固定开销，思考和动作相对短，而一次工具调用可能返回整张表或整个网页。所以瘦身的第一优先级是返回值：截断、摘要、落盘只回传路径。

4. 单步可靠性 98%，跑 10 步，任务整体成功率约多少？

答案约 81.7%（0.9810 ≈ 0.817）。关键点不是记住这个数字，而是记住它是相乘而非相加，以及真实情况更差——因为各步错误是相关的。

5. 为什么没有外部信号的「自我反思」常常无效？

答案反思的输入仍来自模型自身的上下文与先验，是相关样本而非独立证据，结果往往是把同一个偏见说得更自信。有效反思的必要条件是回路中存在外部锚点：测试是否通过、编译器报错、检索到的原文、对账结果、另一个独立模型的判断。

6. Agent 的成本主要来自哪里？给出两个最有效的优化。

答案主要来自每轮把整段历史重新读入，总消耗随步数大致呈平方级增长。两个最有效的优化：① 轨迹压缩与摘要（已完成步骤压成结论）；② 大返回值落盘只回传路径。另外把稳定内容（指令、工具定义）前置以命中前缀缓存。

7. 终止条件应该写在哪里？只靠模型自己判断够不够？

不够终止条件必须写进指令（什么证据算完成、什么情况直接放弃交还人类），并且在此之外加硬护栏：步数上限、预算上限、重复动作检测。只靠模型判断，会遇到两个极端——不终止（无限循环）和过早终止（假装完成）。

8. 举出两种不该用 Agent 的情况。

答案① 任务能被一句话描述清楚、所需信息可一次性放进上下文——一次调用加检索就够了。② 步骤固定且要求高度一致可复现——工作流更便宜、更可预测、更好调试。一般而言，Agent 是用延迟和成本换任务性能，只有当步骤无法事先枚举时才值得。

10 学习路径

  1. 先裸写一次工具调用循环

    不用任何框架，直接用 API 写 20 行：拼上下文 → 调模型 → 解析动作 → 执行 → 回灌 → 判断终止。做完能体会到：Agent 的全部机制就这么点，框架只是省了这些行的写；同时你会亲身体会到解析失败和终止判断才是真正难的部分。

  2. 故意不给终止条件，看它怎么失控

    跑一个开放任务，记录它走了多少步、花了多少钱、在哪一步开始重复。做完能体会到：为什么步数上限和重复动作检测不是可选项，以及轨迹日志为什么必须全量记录。

  3. 给同一个任务配 5 个工具和 20 个工具，对比

    固定任务集，只改工具集规模，统计选错工具的次数与总步数。做完能体会到：「工具越多越强」是错觉，动态裁剪工具集是实实在在的收益。

  4. 把工具返回值原样回灌 vs 截断摘要，对比成本

    同一个任务跑两遍，记录总 token 消耗与成功率。做完能体会到：成本大头在哪里，以及摘要做得好甚至能提升成功率（噪音少了）。

  5. 加一个外部校验器，再跑一遍

    比如让它写代码，每次生成后真实跑测试并把报错原文回灌。做完能体会到：外部反馈才是 Agent 可靠性的真正来源，也是「反思」有效与无效的分界线。

  6. 把能写死的部分抽成工作流，只留不确定部分给模型

    重构你的系统，标出哪些节点是确定性的（解析、校验、格式化、审批）。做完能体会到：真实可用的系统都是混合体，Agent 的边界应该画在「确实无法预设」的地方。

  7. 建一个固定回归任务集，跑 10 遍统计分布

    不要看单次结果，看成功率的分布与失败模式归类。做完能体会到：Agent 的行为是分布不是函数，评估必须批量化；也只有这样，你才知道一次改动到底是变好了还是变差了。

关于卡片里的数字：本卡片只保留了可推导的量（错误累乘为纯数学计算，0.9810 ≈ 81.7% 这类）与定性表述，刻意不写价格、上下文长度、基准分数等易变数字——这类数据变动极快，请以各厂商官方文档为准。

定义来源：Agent 与 workflow 的架构区分采用 Anthropic《Building effective agents》的表述：workflow 由预定义代码路径编排，agent 由模型动态指导自身流程与工具使用。「下一步由谁决定」这条判别式即由此推导而来。
